# AGENTS.md

This file applies to both Codex and GitHub Copilot when they work in this repository. Use it for repository-specific workflow and guardrails, and combine it with any matching agent or instruction file.

## Project Overview

- **Agents** - Specialized GitHub Copilot agents that integrate with MCP servers
- **Instructions** - Coding standards and best practices applied to specific file patterns
- **Skills** - Self-contained folders with instructions and bundled resources for specialized tasks

## Instruction Precedence

- Apply instructions in this order when they conflict: direct user task, deeper path-specific `AGENTS.md`, matching `instructions/*.instructions.md`, this root `AGENTS.md`, then general tool or agent defaults.
- When instructions overlap, prefer the most specific rule that applies to the file or folder you are changing.
- If two instructions at the same scope conflict and the correct interpretation is not obvious, stop and ask for clarification instead of guessing.

## Repository Structure

```
.
|-- agents/           # Custom GitHub Copilot agent definitions (.agent.md files)
|-- instructions/     # Coding standards and guidelines (.instructions.md files)
`-- skills/           # Agent Skills folders (each with SKILL.md and optional bundled assets)
```

## Repo-Specific Working Guidance

- The primary application lives in `src/HERM-MAPPER-APP/` and automated tests live in `tests/HERM-MAPPER-APP.Tests/`.
- The solution targets .NET 10, uses nullable reference types, and enables shared analyzers through `Directory.Build.props`.
- Prefer small, targeted edits that solve the requested problem. Avoid broad refactors unless the task explicitly calls for them.
- Prefer editing source, tests, docs, and scripts. Avoid changing generated or transient content under `bin/`, `obj/`, `artifacts/`, `.artifacts/`, `.tmp/`, `.dotnet-cli/`, `output/`, and `App_Data/` unless the task explicitly targets those paths.
- Do not edit generated code such as `*.g.cs`, `*.designer.cs`, or files marked with `// <auto-generated>` unless the task explicitly requires regenerating or changing generated output.
- Treat `external/` as vendored or imported code. Do not modify it unless the task explicitly requires it.

## Validation Commands

- Use `dotnet build .\HERM-MAPPER-APP.sln -nologo` for a fast solution-level build validation.
- Use `dotnet test .\tests\HERM-MAPPER-APP.Tests\HERM-MAPPER-APP.Tests.csproj -nologo` for targeted test validation.
- Use `test.ps1` when the task should run restore, build, and tests in the repo's standard sequence.
- Use `build.ps1` for release or publish-style validation instead of re-creating publish commands ad hoc.
- Use `start.ps1` or `dotnet run --project .\src\HERM-MAPPER-APP\HERM-MAPPER-APP.csproj` for local application execution.
- Documentation-only or agent/instruction-only changes usually do not require a build or test run.
- Small code changes should get at least the narrowest relevant build or targeted test coverage.
- Behavior changes, bug fixes, or new features should get targeted tests when practical and a solution build at minimum.
- Broad refactors or changes that touch multiple areas should use the repo's standard validation flow with `test.ps1` when practical.

## Test Expectations

- Update or add automated tests when behavior changes, bugs are fixed, or new user-visible logic is introduced.
- If a behavior change is not covered by tests, document the gap and why coverage was not added.
- Prefer targeted tests in `tests/HERM-MAPPER-APP.Tests/` over weaker manual-only validation when practical.

## Analyzer And Config Policy

- Shared analyzer package references belong in `Directory.Build.props`.
- Put solution-wide analyzer defaults in `.globalconfig`.
- Put path-scoped analyzer overrides in `.editorconfig`.
- Prefer fixing analyzer findings over suppressing them. If a rule must be downgraded or suppressed, keep the scope as narrow as possible and document the reason near the configuration or suppression.

## Documentation Expectations

- Update `README.md` when project layout, setup steps, or primary commands change.
- Update the relevant file under `docs/` when behavior changes affect installation, development workflow, configuration, deployment, authentication, or AI features.
- Keep agent and instruction documentation aligned with the actual repo layout and command surface.

## Authoring Conventions

- Add new custom agents under `agents/` using the `.agent.md` suffix.
- Add new instruction files under `instructions/` using the `.instructions.md` suffix and a narrow `applyTo` pattern.
- Keep generic .NET guidance in instruction files and keep repository workflow guidance in `AGENTS.md`.
- Prefer focused agent and instruction files over broad catch-all definitions.
